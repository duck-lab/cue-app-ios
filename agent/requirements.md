# 需求说明

## 项目概述

**cude-app** 是一款支持 iOS 与 macOS 的多平台待办/通知应用。

应用核心目标：

- 从外部系统接收通知（Notification），统一展示并支持处理。
- 支持用户对通知进行「进行中 / 完成 / 忽略」三态管理。
- 支持用户在状态变更时把反馈（含可选补充说明）回传给系统。
- 提供 iOS 与 macOS 平台分别适配的交互体验。

## 功能边界与前提（本阶段）

### 已确定前提

- 无现成 API 文档，优先用 **Mock 数据** + 本地模拟服务实现。
- 保留 API 层接口，后续可替换为真实服务。
- 通知拉取为固定频率：**每 30 秒**。
- 认证能力暂不实现，预留认证接入点。
- 反馈备注支持**自由文本**。
- 通知单条字段至少包含：
  - 标题
  - 来源
  - 优先级
  - 时间戳
  - 额外信息
  - 截止时间（deadline）
  - 状态
- 通知分类方式：按**优先级**和**来源**。
- 状态语义明确：
  - 进行中：用户已开始处理、尚未完成
  - 完成：用户确认已处理完成
  - 忽略：用户明确放弃这条通知
- `完成` 与 `忽略` 是不同业务语义：均可结束当前处理链，但语义不同，需回传系统。
- macOS 菜单栏支持 hover 查看与快速回复。
- iOS 与 macOS 共享同一账号语义，服务器端进行同步；客户端不承担跨端同步存储。
- 单用户场景为主，登录流程在后续迭代中补齐。

### 不在本阶段实现的内容

- 完整登录鉴权与会话管理
- 与真实 API 的联调（保留接口并使用 Mock 数据）
- 通知远程下发的消息加密与高级推送策略（如 APNs 深度配置）

## 用户故事（User Story）

### 通知接收与展示

1. 作为用户，我能在应用内看到一份当前通知列表，包含标题、来源、优先级与时间信息。
2. 作为用户，我能区分未处理、进行中、完成、忽略四种状态。
3. 作为用户，我能按状态、优先级、来源进行筛选和排序。

### 通知处理

1. 作为用户，我能将单条通知标记为「进行中」。
2. 作为用户，我能将单条通知标记为「完成」。
3. 作为用户，我能将单条通知标记为「忽略」。
4. 作为用户，我可在标记时附加说明文字，以便系统收到更多上下文。
5. 作为用户，我在执行状态变更后可以直观看到列表中状态变化。

### 系统反馈

1. 作为用户，我的状态更新会触发向系统提交反馈（或 API 提交请求）。
2. 作为用户，反馈请求中包含状态字段和可选备注。
3. 作为系统，能够记录每一条通知的状态更新时间和来源信息。

### macOS 菜单栏体验

1. 作为 mac 用户，我可将应用最小化到菜单栏。
2. 作为 mac 用户，鼠标 hover 菜单栏时可预览最新通知。
3. 作为 mac 用户，我可在 hover 卡片中快速完成「进行中/完成/忽略」，也可附带可选回复文本。
4. 作为 mac 用户，点击菜单栏图标可展开完整应用窗口并显示全部通知。
5. 作为 mac 用户，菜单栏应显示未读数量（badge）。

### iOS 快速交互

1. 作为 iOS 用户，我可在应用内列表中对通知逐条处理。
2. 作为 iOS 用户，我可在系统通知（推送）上直接进行快速回复。
3. 作为 iOS 用户，快速回复可以是纯状态更新，也可以附加可选文字备注。

## 通知数据模型（v1）

### 核心实体：NotificationItem

- `id`：字符串/UUID
- `title`：标题
- `source`：来源
- `priority`：枚举（Low/Normal/High/Urgent）
- `timestamp`：通知时间
- `deadline`：截止时间（可选）
- `extraInfo`：额外信息（文本）
- `status`：枚举（Pending/InProgress/Completed/Ignored）
- `unread`：是否未读（用于未读计数）
- `replyDraft`：可选备注草稿
- `updatedAt`：最后修改时间

### 通知更新实体：StatusFeedback

- `notificationId`：关联通知 ID
- `status`：目标状态
- `comment`：可选备注
- `timestamp`：反馈时间
- `clientMeta`：客户端元信息（平台、版本、设备）

## 功能拆分（模块化）

### 1. 数据与 API 层

- 定义 `NotificationRepository` 抽象层：统一拉取、更新、反馈接口。
- 默认实现为 `MockNotificationRepository`，提供可复用测试数据。
- 后续扩展真实 API 时不改动 UI 层。

### 2. 同步与更新机制

- 定时任务：每 30 秒触发一次拉取。
- 状态变更触发增量同步。
- 支持失败重试（至少 1 次退避重试）。
- 提供本地变更队列（网络不可用时暂存回传）。

### 3. 核心业务逻辑

- 实现状态机：Pending / InProgress / Completed / Ignored。
- 统一校验：重复提交、冲突提交、无效状态转换的处理。
- 备注字段的长度与空值规则。

### 4. UI 层

- iOS：列表页面、详情或快速处理动作面板。
- macOS：列表 + 菜单栏入口（PopOver/Panel）、悬停预览。
- 菜单栏徽标（未读数）与图标状态。
- 通知卡片：支持分类、优先级颜色、倒计时/截至时间标识。

### 5. 通知与交互

- 本地通知/系统通知展示：收到新通知时给予可见提示与音效。
- iOS 系统通知（UNUserNotificationCenter）：支持操作按钮快速回复。
- 本地化字符串：状态名、提示文案、按钮文案。

### 6. 持久化与状态恢复

- 使用 SwiftData 缓存通知列表，保证离线后可回看。
- 标记与反馈状态与本地持久化同步。

### 7. 平台兼容与测试

- iOS 与 macOS 交互差异（菜单栏、工具栏、快捷操作）独立实现。
- 至少覆盖：
  - 通知列表渲染
  - 状态变更成功路径
  - 失败路径与重试
  - 30 秒轮询触发
  - 本地通知展示

## 非功能性需求

- 可维护性：API 层独立，便于后续接入真实后端。
- 体验性：状态响应应及时（列表操作应在交互后尽量即时反映）。
- 易用性：核心操作控制不超过 2 次交互深度。
- 稳定性：若同步失败，不丢失本地操作，待恢复后回传。

## 里程碑建议（MVP）

### MVP 1：基础通知管理

- 本地 mock 数据源
- 列表展示、三状态处理
- 备注随状态提交
- 本地持久化

### MVP 2：平台能力打通

- macOS 菜单栏 hover 与完整列表弹出
- iOS 系统通知快速回复
- 30 秒定时拉取与状态反馈接口模拟

### MVP 3：体验增强

- 过滤/排序（来源、优先级、状态）
- 本地通知弹窗与声音
- 反馈失败重试与日志可观测

## 验收准则（可测试化）

- 有新通知到达时，应用列表在合理时间内更新。
- 用户可对单条通知执行 3 种状态更新，且状态变更可见。
- 完成/忽略时可附加文字备注并随反馈提交。
- macOS 菜单栏 hover 可预览最近一条通知并提供快速操作。
- 点击 iOS 系统通知可进行快速回复（状态或备注）。
- 应用崩溃后可恢复未处理通知的本地状态。

## 已确认

- API 实现采用 Mock + 可替换接口。
- 轮询固定 30 秒。
- 备注支持自由文本。
- 兼容单用户情景，跨端同步由服务端负责。
- 系统通知与 mac 菜单栏均支持完整操作按钮：进行中 / 完成 / 忽略。
- Mac 菜单栏 hover 中支持状态操作的同时，可输入补充文本（可选）。
- Menubar 未读 badge 按 `unread` 字段计数。
